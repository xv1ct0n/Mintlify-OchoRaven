# Network forensics with Wireshark

Network forensics is the process of reconstructing and interpreting network activity from captured traffic and related telemetry. In this lab, you will use Wireshark to move from raw packets to defensible observations, then learn how those observations connect to Security Onion, Arkime, Suricata, and SIEM data.

<Info>
**Audience:** Beginner through intermediate cybersecurity professionals. You should understand basic IP addressing and have seen TCP, UDP, DNS, and HTTP before. Advanced sections are optional.

**Outcome:** You will be able to open a PCAP, establish scope, use display filters, reconstruct conversations, investigate DNS and HTTP activity, identify evidence worth escalating, document findings, and pivot between packet data and common defensive platforms.
</Info>

## Prerequisites

You need:

- Wireshark installed on a lab workstation, or Wireshark available through a Security Onion Desktop environment;
- a benign or authorized PCAP;
- basic familiarity with source/destination IP addresses and ports;
- permission to inspect the traffic you use.

You do **not** need Security Onion, Arkime, Elasticsearch/OpenSearch, or Suricata to complete the core lab.

<Warning>
Use packet captures from systems you own, training datasets, or environments where you have explicit authorization. Packet captures can contain credentials, cookies, personal information, internal hostnames, and other sensitive data.
</Warning>

## Core terminology

| Term | Plain-language meaning |
| --- | --- |
| Packet | A unit of network data transmitted between systems. |
| PCAP | A file containing captured packets. |
| Flow/session | A related conversation between network endpoints. |
| Protocol dissector | Wireshark logic that interprets bytes as a known protocol. |
| Display filter | A Wireshark expression that hides packets that do not match your current analysis. |
| Capture filter | A libpcap/BPF expression that controls what is recorded during capture. |
| Stream | A reconstructed conversation, such as a TCP connection. |
| Artifact | A piece of evidence derived from traffic, such as a hostname, URI, IP, file hash, or user agent. |

## Capture filters are not display filters

This distinction is essential.

A **capture filter** limits what is recorded. For example:

```text
host 192.0.2.25 and port 53
```

A **display filter** operates on packets that have already been captured:

```text
ip.addr == 192.0.2.25 && dns
```

Wireshark uses libpcap syntax for capture filters and its own display-filter language for analysis. Do not assume syntax can be copied between them.

# Investigation workflow

Use the same high-level workflow each time you open a PCAP:

```text
Define the question
      ↓
Establish capture scope
      ↓
Identify endpoints and protocols
      ↓
Reduce noise with filters
      ↓
Inspect conversations
      ↓
Extract relevant artifacts
      ↓
Correlate with other telemetry
      ↓
Document evidence and limitations
```

Do not begin by searching randomly for something that "looks malicious." Start with a question and progressively narrow the evidence.

# Lab — Investigate a packet capture

## Purpose

Practice a repeatable workflow that resembles a real alert-validation or threat-hunting pivot.

## Environment

Use one of these safe options:

1. capture traffic generated by your own lab workstation;
2. use a benign Wireshark sample capture;
3. use a training PCAP already approved by your organization;
4. export authorized PCAP from Security Onion or Arkime.

For a first attempt, generate a small capture yourself by browsing a few non-sensitive sites and performing DNS lookups. This makes the expected activity easier to understand.

## Step 1 — Open the capture

Open Wireshark and select **File → Open**, then select your `.pcap` or `.pcapng` file.

Wireshark's primary packet view contains three important areas:

- **Packet List** — one row per packet;
- **Packet Details** — decoded protocol fields for the selected packet;
- **Packet Bytes** — the underlying bytes represented in hexadecimal and text where possible.

### Validation

You should see packet rows with columns such as time, source, destination, protocol, length, and info.

If the file opens but contains no packets, verify that the source capture is not empty.

---

## Step 2 — Establish capture scope

Before filtering, answer:

- When does the capture begin and end?
- Approximately how many packets are present?
- Which hosts appear most frequently?
- Which protocols dominate the capture?

Use **Statistics → Capture File Properties** for capture metadata.

Then inspect:

- **Statistics → Protocol Hierarchy**;
- **Statistics → Endpoints**;
- **Statistics → Conversations**.

### Why this matters

A 30-second workstation capture and a 24-hour sensor capture require different expectations. Scope prevents you from treating absence of evidence as evidence that an event did not happen outside the capture window.

### Analyst notes

Record at minimum:

```text
Capture start:
Capture end:
Packet count:
Primary internal host(s):
Notable protocols:
Initial question:
```

---

## Step 3 — Identify a host of interest

Choose one lab endpoint and filter around it:

```text
ip.addr == 192.0.2.25
```

Replace the example address with an IP that exists in your capture.

`ip.addr` matches the address when it appears as either source or destination.

To be directional:

```text
ip.src == 192.0.2.25
```

or:

```text
ip.dst == 192.0.2.25
```

### Concrete use case

If an alert identifies `192.0.2.25` as a suspected workstation, `ip.addr == 192.0.2.25` gives you an initial packet-level view of activity involving that system.

---

## Step 4 — Investigate DNS

Apply:

```text
dns
```

To focus on DNS involving your host:

```text
ip.addr == 192.0.2.25 && dns
```

Queries can be narrowed with fields such as:

```text
dns.flags.response == 0
```

Responses:

```text
dns.flags.response == 1
```

Search for a known domain when your capture contains it:

```text
dns.qry.name == "example.com"
```

### What to inspect

Expand **Domain Name System** in Packet Details and identify:

- query name;
- query type;
- response code;
- returned IP addresses;
- timing between query and response.

### Cybersecurity example

An endpoint alert may contain only an IP address. DNS traffic can show which hostname the workstation attempted to resolve before connecting to that address. That relationship can provide useful investigative context.

<Warning>
A DNS lookup does not prove a subsequent connection occurred. Treat resolution and connection as separate observations until you correlate them.
</Warning>

---

## Step 5 — Examine TCP connections

Filter TCP:

```text
tcp
```

Initial SYN packets can help identify connection attempts:

```text
tcp.flags.syn == 1 && tcp.flags.ack == 0
```

Combine with your host:

```text
ip.src == 192.0.2.25 && tcp.flags.syn == 1 && tcp.flags.ack == 0
```

### TCP handshake

A normal connection commonly begins:

```text
Client → Server   SYN
Server → Client   SYN, ACK
Client → Server   ACK
```

Select a packet and inspect **Transmission Control Protocol** in Packet Details.

### Useful questions

- Which destination ports does the host contact?
- Are connection attempts answered?
- Are resets (`RST`) common?
- Is one destination contacted repeatedly?
- Does the connection carry an identifiable application protocol?

---

## Step 6 — Follow a stream

Select a TCP packet, right-click it, then choose **Follow → TCP Stream**.

Wireshark reconstructs application bytes carried by that conversation when they are available.

You can also filter a known stream number:

```text
tcp.stream == 3
```

Replace `3` with a stream number from your capture.

### Why stream reconstruction matters

Individual packets are fragments of a conversation. Following the stream lets you reason about the interaction as a whole rather than interpreting isolated packets.

### Encryption limitation

For TLS-encrypted application data, packet capture usually exposes metadata such as endpoints, timing, sizes, TLS handshake information, and certificates, but not plaintext application content unless appropriate decryption material is available and authorized.

---

## Step 7 — Investigate HTTP when present

If your authorized sample contains unencrypted HTTP:

```text
http
```

Requests:

```text
http.request
```

GET requests:

```text
http.request.method == "GET"
```

Responses:

```text
http.response
```

Useful fields may include:

```text
http.host
http.request.uri
http.user_agent
http.response.code
```

### Example investigative questions

```text
What host was requested?
What URI was requested?
Which user agent generated the request?
What response status was returned?
Did the conversation transfer an object?
```

<Info>
Modern web traffic is commonly encrypted with TLS, so do not expect every web connection to expose HTTP fields. Wireshark can only dissect fields that are available from the captured traffic and supported protocol context.
</Info>

---

## Step 8 — Export an HTTP object in the lab

When your **benign training capture** contains an HTTP file transfer, use:

**File → Export Objects → HTTP**

Review the object list and save only the lab artifact you intend to inspect.

### Validation

Hash the exported file instead of immediately executing or opening unknown content:

Linux/macOS:

```bash
sha256sum exported-file.bin
```

PowerShell:

```powershell
Get-FileHash .\exported-file.bin -Algorithm SHA256
```

This connects directly to the file-hashing skills in the Python training path.

<Warning>
Do not execute files extracted from untrusted packet captures. Analyze suspicious artifacts in an appropriately isolated environment according to your organization's procedures.
</Warning>

## Step 9 — Use TShark for repeatable analysis

TShark is Wireshark's command-line packet analyzer. It uses the same display-filter engine.

Read a PCAP:

```bash
tshark -r lab.pcapng
```

Apply a display filter:

```bash
tshark -r lab.pcapng -Y "dns"
```

Extract selected fields:

```bash
tshark -r lab.pcapng \
  -Y "dns.flags.response == 0" \
  -T fields \
  -e frame.time \
  -e ip.src \
  -e dns.qry.name
```

### Why this matters

GUI analysis is excellent for exploration. TShark lets you make parts of the workflow repeatable and provides a bridge into Python, shell scripting, and larger analysis pipelines.

# Useful display filters

These are starting points, not universal detections.

| Objective | Wireshark display filter |
| --- | --- |
| One IP in either direction | `ip.addr == 192.0.2.25` |
| Traffic between two IPv4 hosts | `ip.addr == 192.0.2.25 && ip.addr == 198.51.100.10` |
| DNS | `dns` |
| DNS queries | `dns.flags.response == 0` |
| TCP initial SYN | `tcp.flags.syn == 1 && tcp.flags.ack == 0` |
| TCP resets | `tcp.flags.reset == 1` |
| One TCP stream | `tcp.stream == 3` |
| HTTP requests | `http.request` |
| TLS | `tls` |
| ICMP | `icmp` |

Use the official Wireshark Display Filter Reference when a field is version-dependent or unfamiliar.

# Pivoting from Security Onion

Security Onion can provide the alert, hunt result, or session context that tells you **where to start**. PCAP then provides packet-level evidence.

A common workflow is:

```text
Security Onion alert/hunt
        ↓
Identify host + time + ports
        ↓
Pivot to PCAP
        ↓
Download/open in Wireshark
        ↓
Reconstruct packet evidence
```

Current Security Onion documentation describes Wireshark as part of Security Onion Desktop and documents downloading PCAP for analysis. Its full-packet-capture documentation also describes pivots from Alerts, Dashboards, and Hunt.

# Pivoting from Arkime

Arkime organizes packet data into searchable sessions. Use Arkime to narrow a large capture environment by time, IP, port, protocol, or other indexed session fields, then export relevant PCAP for deeper Wireshark analysis.

```text
Arkime search
    ↓
Relevant session(s)
    ↓
Export PCAP
    ↓
Wireshark analysis
```

Arkime's current documentation supports PCAP export from session search results and provides APIs for retrieving session PCAP.

<Card title="Arkime documentation" icon="network-wired" href="https://arkime.com/">
Review session search, packet views, and PCAP export capabilities in the maintained Arkime documentation.
</Card>

Do not copy Wireshark display-filter syntax into Arkime searches. Arkime uses its own search expressions and indexed fields.

# Correlating Suricata alerts with packets

Suricata can generate EVE JSON events containing fields such as source/destination addresses, ports, protocol, alert signature information, and flow identifiers.

When Suricata processes a PCAP, EVE records can also include `pcap_cnt`, which identifies a packet number in the source PCAP. This can provide a direct pivot back to Wireshark for supported event types.

Example conceptual workflow:

```text
Suricata alert
  src_ip: 192.0.2.25
  dest_ip: 198.51.100.10
  dest_port: 80
  pcap_cnt: 53381
        ↓
Open source PCAP in Wireshark
        ↓
Go to packet 53381
        ↓
Inspect surrounding stream
```

</Card>

# Elasticsearch, OpenSearch, and Kibana context

Elasticsearch/OpenSearch and their visualization/query interfaces operate on **indexed events**, not raw packet bytes unless you have explicitly ingested packet-derived data.

Use them to locate context such as:

```text
source IP
Destination IP
ports
DNS fields
HTTP metadata
Suricata alert fields
timestamps
flow/session identifiers
```

Then pivot to packet data when available.

<Warning>
Query syntax is platform-specific. Kibana may expose KQL, Lucene, ES|QL, or other Elasticsearch-backed workflows depending on version and application. OpenSearch Dashboards supports OpenSearch-specific query capabilities. Wireshark display filters are a separate language. Translate the **investigative question**, not the literal query string.
</Warning>

A useful mental model is:

```text
SIEM / indexed telemetry → find the needle
Arkime / session metadata → find the conversation
Wireshark / PCAP          → inspect the packets
```

# YARA and packet analysis

YARA is primarily designed to match patterns in files or data, not to replace Wireshark's protocol analysis.

A defensible workflow is:

```text
PCAP
 ↓
Wireshark identifies a transferred object
 ↓
Export object in an isolated lab
 ↓
Hash / inspect artifact
 ↓
Apply approved YARA rules to the extracted file
```

Do not describe a YARA match as equivalent to a network IDS alert. They operate on different evidence and rule models.

# Snort and Suricata versus Wireshark

| Tool | Primary role | Typical output |
| --- | --- | --- |
| Wireshark | Interactive protocol and packet analysis | Analyst observations, streams, packet details |
| TShark | Scriptable packet analysis | Text/structured field output |
| Suricata | Network IDS/IPS and protocol telemetry | Alerts, EVE JSON, flow/application events |
| Snort | Network IDS/IPS | Rule-based alerts and related telemetry |
| Arkime | Full-packet capture indexing and session search | Searchable sessions and retrievable PCAP |

These tools complement one another. Do not assume Suricata or Snort rule syntax, Arkime expressions, and Wireshark filters are interchangeable.

# Validation exercise

Complete the following using your benign capture:

<Steps>
  <Step title="Scope the capture">
    Record capture start/end time, packet count, and the primary host you will investigate.
  </Step>
  <Step title="Identify protocols">
    Use Protocol Hierarchy and list the three most relevant protocols for your investigation.
  </Step>
  <Step title="Analyze DNS">
    Identify at least one DNS query and its response. Record the queried name and returned address when present.
  </Step>
  <Step title="Analyze a connection">
    Identify a TCP connection and determine the source, destination, destination port, and whether a handshake completed.
  </Step>
  <Step title="Reconstruct a stream">
    Follow one TCP stream and describe what metadata or plaintext is visible.
  </Step>
  <Step title="Create an evidence note">
    Write one factual observation, one interpretation, and one limitation. Keep them separate.
  </Step>
</Steps>

Example structure:

```text
Observation:
Host 192.0.2.25 queried example.com and received 198.51.100.10.

Interpretation:
The DNS exchange provides evidence that the host resolved the domain during the capture window.

Limitation:
The DNS exchange alone does not prove the host established a subsequent connection to the returned address.
```

# Troubleshooting

## My filter turns red

The expression is invalid for the current Wireshark display-filter parser. Check field names and operators in the official Display Filter Reference. Also confirm that you are not entering capture-filter syntax into the display-filter bar.

## I see TCP but no HTTP

The traffic may be TLS-encrypted, use HTTP/2 or HTTP/3, run on a nonstandard protocol/port, lack enough packets for dissection, or simply not contain HTTP. Start with the packet details rather than forcing a protocol assumption.

## Follow TCP Stream is incomplete

The PCAP may begin after the conversation started, packets may be missing, capture loss may have occurred, or only one network direction may have been recorded.

## I cannot find the alert packet from my SIEM

Confirm timestamps and time zones, source/destination direction, NAT effects, capture retention, sensor placement, and whether full packet capture was enabled for the relevant traffic.

## Security Onion has event data but no PCAP

Verify full-packet-capture configuration and retention for your deployed Security Onion version. Event telemetry can exist even when the corresponding raw packets are unavailable.

## Translate questions across tools

Take this question:

> What DNS activity did host `192.0.2.25` generate during the investigation window?

Represent it conceptually in each environment:

```text
Wireshark → filter packets by host + DNS
Arkime    → search sessions/fields for host + DNS
SIEM      → query indexed DNS events for host + time
Suricata  → inspect DNS EVE records for host + time
```

The syntax differs, but the investigative question remains stable.

## Automate with TShark

Export DNS questions:

```bash
tshark -r lab.pcapng \
  -Y "dns.flags.response == 0" \
  -T fields \
  -E header=y \
  -E separator=, \
  -e frame.time_epoch \
  -e ip.src \
  -e ip.dst \
  -e dns.qry.name
```

Save the output:

```bash
tshark -r lab.pcapng \
  -Y "dns.flags.response == 0" \
  -T fields \
  -E header=y \
  -E separator=, \
  -e frame.time_epoch \
  -e ip.src \
  -e ip.dst \
  -e dns.qry.name > dns_queries.csv
```

This provides a natural next step into Python-based packet-processing and detection-engineering projects.

# Completion criteria

You are ready to move beyond this lab when you can:

- explain the difference between capture and display filters;
- establish the scope and limitations of a PCAP;
- identify major endpoints, conversations, and protocols;
- filter by host, protocol, field, and TCP stream;
- analyze basic DNS and TCP behavior;
- follow a TCP stream;
- inspect HTTP metadata when plaintext HTTP exists;
- safely extract a benign lab object and calculate its hash;
- reproduce a useful filter with TShark;
- pivot conceptually from Security Onion, Arkime, or Suricata to PCAP;
- separate packet observations from analytical interpretations;
- document limitations caused by encryption, missing packets, sensor placement, or retention.
