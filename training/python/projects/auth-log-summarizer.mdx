# Project 2 — Authentication Log Summarizer

Project 1 taught you how to turn inconsistent strings into structured IOC records. Project 2 moves closer to day-to-day defensive analysis: you will process a stream of authentication events, summarize activity, and identify a simple behavioral pattern worth analyst review.

<Info>
**Final capability:** Build `auth_summarizer.py`, a command-line tool that reads synthetic JSONL authentication telemetry, validates events, counts successes and failures by user and source IP, identifies repeated failures followed by a success, prints an analyst summary, and exports a structured JSON report.
</Info>

## Operational intent

Authentication telemetry is central to SOC monitoring, threat hunting, incident response, and identity-focused detection engineering. Analysts frequently need to answer questions such as:

- Which accounts are experiencing the most failures?
- Which source IPs are generating failures?
- Did a series of failures eventually result in a successful login?
- When did the activity occur?
- What source and destination were involved?

This project teaches the Python patterns needed to answer those questions repeatably.

<Warning>
A sequence of failed logins followed by a success is **not proof of compromise**. Users mistype passwords, applications retry credentials, and administrators perform legitimate testing. The tool produces an analytical lead for review, not a verdict.
</Warning>

# Lesson 1 — Understand authentication telemetry

Before writing detection logic, understand the data.

For this project, every authentication event will contain:

| Field | Meaning |
| --- | --- |
| `timestamp` | When the event occurred |
| `username` | Account attempting authentication |
| `source_ip` | Address initiating the authentication |

## Why JSONL?

JSON Lines stores one JSON object per line. This resembles many exported security datasets and allows a program to process events individually rather than loading one giant JSON array.

```text
line 1 → event
line 2 → event
line 3 → event
```

That becomes important when datasets grow.

# Lesson 2 — Parse one event

Import JSON:

```python
import json
```

A line from the file is initially just a string. `json.loads()` converts that string into Python objects.

```python
line = '{"username":"alice","result":"failure"}'
event = json.loads(line)

print(event)
print(event["username"])
```

Expected:

```text
{'username': 'alice', 'result': 'failure'}
alice
```

## Dictionaries revisited

An event is naturally represented as a dictionary because each field has a name.

```python
username = event["username"]
result = event["result"]
```

If a required key is missing, direct access raises `KeyError`. In security telemetry, malformed or incomplete events should be expected rather than assumed impossible.

# Lesson 3 — Validate event structure

Define the fields your program requires:

```python
REQUIRED_FIELDS = {
    "timestamp",
    "username",
    "source_ip",
    "destination",
    "result",
    "event_id",
}
```

Create a validator:

```python
def validate_event(event: dict) -> tuple[bool, str | None]:
    """Validate the fields required by this project."""
    missing = REQUIRED_FIELDS - event.keys()

    if missing:
        return False, f"missing fields: {', '.join(sorted(missing))}"

    if event["result"] not in {"success", "failure"}:
        return False, "result must be success or failure"

    return True, None
```

## New concept: set difference

`REQUIRED_FIELDS - event.keys()` asks: which required fields are not present in the event?

This is clearer than writing six separate `if` statements.

## Why return two values?

The function returns both a Boolean result and an explanation:

```python
valid, reason = validate_event(event)
```

This makes rejected telemetry explainable.

# Lesson 5 — Read JSONL safely

Create the reader:

```python
from pathlib import Path


def read_events(file_path: Path) -> tuple[list[dict], list[dict]]:
    """Read and validate JSONL authentication events."""
    events = []
    rejected = []

    with file_path.open("r", encoding="utf-8") as file:
        for line_number, line in enumerate(file, start=1):
            line = line.strip()

            if not line:
                continue

            try:
                event = json.loads(line)
            except json.JSONDecodeError as exc:
                rejected.append({
                    "line": line_number,
                    "reason": f"invalid JSON: {exc.msg}",
                })
                continue

            if not isinstance(event, dict):
                rejected.append({
                    "line": line_number,
                    "reason": "event must be a JSON object",
                })
                continue

            valid, reason = validate_event(event)

            if not valid:
                rejected.append({"line": line_number, "reason": reason})
                continue

            try:
                event["_timestamp"] = parse_timestamp(event["timestamp"])
            except (TypeError, ValueError):
                rejected.append({
                    "line": line_number,
                    "reason": "invalid timestamp",
                })
                continue

            events.append(event)

    return events, rejected
```

## New concept: `enumerate()`

`enumerate()` gives you both an item and its position:

```python
for line_number, line in enumerate(file, start=1):
```

Line numbers make error reports actionable. "Invalid JSON" is less useful than "Invalid JSON on line 14."

## Why keep rejected records?

Silently discarding malformed telemetry can hide collection or parsing problems. Defensive tooling should make data-quality failures visible.

# Lesson 6 — Sort the timeline

Even if the sample file is ordered, never build sequence logic around that assumption unless the data contract guarantees it.

```python
def sort_events(events: list[dict]) -> list[dict]:
    """Return events sorted by parsed timestamp."""
    return sorted(events, key=lambda event: event["_timestamp"])
```

## New concept: `lambda`

A lambda is a small anonymous function. Here it tells `sorted()` which value to use as the sort key.

Equivalent longer form:

```python
def timestamp_key(event):
    return event["_timestamp"]
```

For a tiny operation, the lambda is concise.

# Lesson 7 — Count outcomes by user

Python's `Counter` is designed for counting hashable values.

```python
from collections import Counter
```

Start simple:

```python
failures_by_user = Counter()

for event in events:
    if event["result"] == "failure":
        failures_by_user[event["username"]] += 1
```

Result conceptually:

```python
Counter({"alice": 3, "charlie": 2})
```

Now build a complete user summary:

```python
def summarize_users(events: list[dict]) -> dict[str, dict[str, int]]:
    """Count authentication outcomes for each username."""
    summary = {}

    for event in events:
        username = event["username"]

        if username not in summary:
            summary[username] = {"successes": 0, "failures": 0}

        if event["result"] == "success":
            summary[username]["successes"] += 1
        else:
            summary[username]["failures"] += 1

    return summary
```

## Nested dictionaries

The structure becomes:

```python
{
    "alice": {
        "successes": 1,
        "failures": 3
    }
}
```

This is a common pattern in analysis programs: an entity key maps to a collection of metrics about that entity.

# Lesson 8 — Count failures by source IP

This task is a good fit for `Counter`:

```python
def failures_by_source(events: list[dict]) -> Counter:
    """Count failed authentications by source IP."""
    counts = Counter()

    for event in events:
        if event["result"] == "failure":
            counts[event["source_ip"]] += 1

    return counts
```

Try:

```python
print(failures_by_source(events).most_common())
```

`most_common()` sorts the highest counts first, which is useful for analyst triage.

## Analytical caution

High failure counts can be useful prioritization signals, but volume alone does not establish maliciousness. Context matters: source type, user population, time window, authentication protocol, expected automation, and environment all influence interpretation.

# Lesson 9 — Group events by account

To detect a sequence such as failures followed by success, group events by username.

Import:

```python
from collections import defaultdict
```

Add:

```python
def group_by_user(events: list[dict]) -> dict[str, list[dict]]:
    """Group chronologically sorted events by username."""
    grouped = defaultdict(list)

    for event in events:
        grouped[event["username"]].append(event)

    return dict(grouped)
```

## Why `defaultdict(list)`?

With a normal dictionary, you would need to initialize a list before appending:

```python
if username not in grouped:
    grouped[username] = []
```

A `defaultdict(list)` creates an empty list automatically when a new key is encountered.

# Lesson 10 — Think about detection as state

Suppose the threshold is three failures.

For Alice:

```text
10:00 failure
10:01 failure
10:03 failure
10:04 success
```

The program must remember that three failures occurred before the success.

This is **stateful analysis**. The meaning of the current event depends on what happened earlier.

A simple state variable can represent that history:

```python
consecutive_failures = 0
```

On failure:

```python
consecutive_failures += 1
```

On success, inspect the state and then reset it:

```python
if consecutive_failures >= threshold:
    # create finding

consecutive_failures = 0
```

This idea appears repeatedly in detection engineering, streaming analytics, protocol analysis, and behavioral monitoring.

# Lesson 11 — Detect failures followed by success

Create:

```python
def detect_failure_then_success(
    events: list[dict], threshold: int
) -> list[dict]:
    """Find users with threshold consecutive failures followed by success."""
    findings = []
    grouped = group_by_user(events)

    for username, user_events in grouped.items():
        consecutive_failures = 0
        first_failure = None
        last_failure = None
        failure_sources = set()

        for event in user_events:
            if event["result"] == "failure":
                if consecutive_failures == 0:
                    first_failure = event

                consecutive_failures += 1
                last_failure = event
                failure_sources.add(event["source_ip"])
                continue

            if event["result"] == "success":
                if consecutive_failures >= threshold:
                    findings.append({
                        "username": username,
                        "failure_count": consecutive_failures,
                        "first_failure": first_failure["timestamp"],
                        "last_failure": last_failure["timestamp"],
                        "success_time": event["timestamp"],
                        "failure_source_ips": sorted(failure_sources),
                        "success_source_ip": event["source_ip"],
                        "destination": event["destination"],
                    })

                consecutive_failures = 0
                first_failure = None
                last_failure = None
                failure_sources = set()

    return findings
```

## Walk through the logic

The outer loop analyzes one account at a time. The inner loop moves chronologically through that account's events.

`consecutive_failures` records how many failures have occurred since the last success.

`first_failure` and `last_failure` preserve timeline context.

`failure_sources` preserves all source IPs involved in the failure sequence.

When a success arrives, the program asks whether the prior failure count met the configured threshold. If so, it creates a finding.

Then the state resets for the next sequence.

<Warning>
This beginner analytic does not yet implement a time window. Three failures over six months followed by a success would still match if they were consecutive in the dataset. You will address this limitation in a stretch exercise.
</Warning>

# Lesson 13 — Build an overall summary

Create a report structure that separates high-level metrics from detailed findings.

```python
def build_report(events: list[dict], rejected: list[dict], threshold: int) -> dict:
    user_summary = summarize_users(events)
    source_failures = failures_by_source(events)
    findings = detect_failure_then_success(events, threshold)

    success_count = sum(1 for event in events if event["result"] == "success")
    failure_count = sum(1 for event in events if event["result"] == "failure")

    return {
        "summary": {
            "total_events": len(events),
            "successful_authentications": success_count,
            "failed_authentications": failure_count,
            "unique_users": len(user_summary),
            "rejected_records": len(rejected),
            "failure_threshold": threshold,
            "findings": len(findings),
        },
        "users": user_summary,
        "failures_by_source_ip": dict(source_failures.most_common()),
        "findings": findings,
        "rejected": rejected,
    }
```

## New concept: generator expressions

This expression:

```python
sum(1 for event in events if event["result"] == "success")
```

means: generate a `1` for every matching event and sum those values.

It avoids building an unnecessary intermediate list.

# Lesson 14 — Keep internal fields out of output

Earlier, you added `_timestamp` to each event for sorting. The underscore is a convention indicating that the field is internal to your program.

Your final report does not need to export the raw event list, so `_timestamp` never needs to be serialized. This illustrates a useful design principle:

```text
input representation ≠ internal representation ≠ output representation
```

A program may transform data internally for analysis without exposing every implementation detail in its output.

```python
def main() -> int:

        events = sort_events(events)
        report = build_report(events, rejected, args.failure_threshold)
        write_report(report, args.output)
    except (OSError, UnicodeError) as exc:
        print(f"Error: {exc}")
        return 1

    print_summary(report)
    print(f"\nReport written to: {args.output}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

### Invalid JSON

```text
this is not json
```

### Missing field

```json
{"timestamp":"2026-01-15T11:00:00Z","username":"dave","result":"failure"}
```

### Unsupported result

```json
{"timestamp":"2026-01-15T11:01:00Z","username":"dave","source_ip":"192.0.2.50","destination":"server-01","result":"unknown","event_id":2001}
```

### Invalid timestamp

```json
{"timestamp":"yesterday","username":"dave","source_ip":"192.0.2.50","destination":"server-01","result":"failure","event_id":2002}
```

The application should continue processing valid records while recording why invalid records were rejected.

This is an important operational property: one malformed event should not necessarily destroy an entire batch analysis.

# Independent challenge — Add a time window

The current analytic has an important weakness: it counts consecutive failures regardless of how much time passed between them.

Improve the command:

```bash
python3 auth_summarizer.py sample_auth.jsonl \
  --failure-threshold 3 \
  --window-minutes 10
```

Desired behavior:

```text
3 failures within 10 minutes → followed by success → finding
3 failures across 4 hours → followed by success → no finding
```

Hints:

- you already have `_timestamp` as a `datetime`;
- subtracting two datetime objects creates a `timedelta`;
- compare the elapsed duration to your configured window;
- think carefully about when old failures should leave the active sequence.

Do not immediately search for a completed solution. Draw the state transitions first.
