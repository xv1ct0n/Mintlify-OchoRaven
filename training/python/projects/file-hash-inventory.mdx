# Project 3 — File Hash Inventory

Projects 1 and 2 taught you to normalize indicators and analyze event telemetry. Project 3 shifts from structured security data to the filesystem. You will build a tool that recursively discovers files, collects metadata, calculates SHA-256 hashes, handles inaccessible files, and exports a reusable inventory.

<Info>
**Final capability:** Build `hash_inventory.py`, a command-line utility that recursively inventories an authorized directory, calculates SHA-256 hashes without loading entire files into memory, records file metadata, continues through recoverable errors, prints a concise summary, and exports CSV and JSON results.
</Info>

## Operational intent

File hashes are commonly used in defensive workflows for integrity checking, incident scoping, malware triage, allow/block-list support, duplicate identification, and comparison of filesystem state over time.

A hash answers a narrow question: **do these bytes produce the same digest?** It does not determine whether a file is malicious.

<Warning>
A SHA-256 value is an identifier derived from file contents, not a malware verdict. A known hash may provide useful context, but classification requires additional evidence.
</Warning>

# Lesson 4 — Discover files recursively

Use `rglob()`:

```python
for path in root.rglob("*"):
    print(path)
```

This returns files and directories beneath the root.

Filter to files:

```python
for path in root.rglob("*"):
    if path.is_file():
        print(path)
```

Create a function:

```python
def discover_files(root: Path) -> list[Path]:
    """Return regular files recursively discovered beneath root."""
    return sorted(path for path in root.rglob("*") if path.is_file())
```

## Why sort?

Filesystem traversal order can vary. Sorting gives the tool predictable output, which helps testing and comparison.

<Info>
Deterministic output is a valuable engineering property. The same input should produce the same ordering whenever practical.
</Info>

# Lesson 5 — Understand binary file I/O

In earlier projects you mostly read text using:

```python
file.open("r", encoding="utf-8")
```

Hashes must be calculated over the file's **raw bytes**.

Binary mode uses `rb`:

```python
with path.open("rb") as file:
    data = file.read()
```

The `b` means binary.

A Python byte string looks like:

```python
b"example"
```

## Why not decode the file first?

Decoding interprets bytes as text and can fail or alter representation. A file hash must reflect the original byte sequence exactly.

# Lesson 6 — Calculate your first SHA-256

Import:

```python
import hashlib
```

Try:

```python
data = b"hello"
digest = hashlib.sha256(data).hexdigest()
print(digest)
```

`hashlib.sha256()` creates or computes a SHA-256 hash.

`hexdigest()` returns the digest as hexadecimal text.

For identical bytes:

```text
same bytes → same SHA-256
```

A changed byte should normally produce a very different digest.

## Defensive use

This property lets analysts compare files without manually comparing every byte. It is useful for answering questions such as:

```text
Is this collected file identical to another sample?
Did this file change between two inventories?
Which hosts contain files with the same content?
```

# Lesson 7 — Why reading an entire file is a problem

This works for tiny files:

```python
data = file.read()
```

But imagine hashing a 20 GB disk image or archive. Loading the entire file into RAM is unnecessary.

Instead, read a small block, update the hash, then read the next block:

```text
file
 ↓
[chunk 1] → hash.update()
[chunk 2] → hash.update()
[chunk 3] → hash.update()
...
 ↓
final digest
```

This is **streaming I/O**.

---

# Lesson 8 — Hash files in chunks

Define a chunk size:

```python
CHUNK_SIZE = 1024 * 1024
```

That is 1 MiB.

Create the function:

```python
def sha256_file(path: Path) -> str:
    """Calculate a file's SHA-256 digest using streaming reads."""
    digest = hashlib.sha256()

    with path.open("rb") as file:
        while chunk := file.read(CHUNK_SIZE):
            digest.update(chunk)

    return digest.hexdigest()
```

## New concept: the walrus operator

This line:

```python
while chunk := file.read(CHUNK_SIZE):
```

assigns the bytes to `chunk` and evaluates whether data was returned.

When end-of-file is reached, `read()` returns `b""`, which is falsy, so the loop ends.

Equivalent longer code would be:

```python
while True:
    chunk = file.read(CHUNK_SIZE)

    if not chunk:
        break

    digest.update(chunk)
```

Either form is valid. Use the one you understand most clearly.

```text
Version A bytes → hash A
```

# Lesson 10 — Collect file metadata

A hash is more useful when accompanied by context.

Python's `stat()` provides filesystem metadata:

```python
metadata = path.stat()
print(metadata.st_size)
```

`st_size` is the file size in bytes.

Create an inventory record:

```python
def inventory_file(path: Path, root: Path) -> dict:
    """Create an inventory record for one file."""
    metadata = path.stat()

    return {
        "path": path.relative_to(root).as_posix(),
        "size_bytes": metadata.st_size,
        "sha256": sha256_file(path),
    }
```

## Why `relative_to()`?

If the full path is:

```text
/home/analyst/project/samples/nested/example.bin
```

and `root` is:

```text
/home/analyst/project/samples
```

then:

```python
path.relative_to(root)
```

becomes:

```text
nested/example.bin
```

## Why `as_posix()`?

It produces `/`-separated paths consistently in the report, including when Python is running on Windows.

# Lesson 11 — Handle errors per file

A directory may contain a file that disappears, becomes inaccessible, or cannot be read.

A fragile program might terminate the entire scan.

A resilient inventory should instead record the error and continue.

```python
def build_inventory(root: Path) -> tuple[list[dict], list[dict]]:
    """Inventory files beneath root while preserving recoverable errors."""
    records = []
    errors = []

    for path in discover_files(root):
        try:
            records.append(inventory_file(path, root))
        except OSError as exc:
            errors.append({
                "path": path.relative_to(root).as_posix(),
                "error": str(exc),
            })

    return records, errors
```

## Error scope matters

Notice where `try` appears: **inside the loop**.

```text
file 1 → success
file 2 → error → record error
file 3 → success
file 4 → success
```

If the exception handler surrounded the entire loop, one failure could prevent later files from being processed.

This is a major lesson for defensive automation: decide whether an error should terminate the **item**, the **batch**, or the **program**.

# Lesson 12 — Consider filesystem race conditions

A file can change between discovery, metadata collection, and hashing.

For example:

```text
1. discover report.log
2. collect size
3. another process modifies report.log
4. calculate hash
```

Your metadata and digest may then describe slightly different states.

This is sometimes called a time-of-check/time-of-use problem.

For a beginner inventory tool, document this limitation rather than attempting complex filesystem snapshotting.

<Info>
Good engineering includes knowing what your program **cannot guarantee**. Production forensic acquisition and integrity systems may use snapshots, filesystem-specific mechanisms, or controlled evidence procedures.
</Info>

# Lesson 15 — Find duplicate content

If two files have the same SHA-256, they contain the same byte sequence for practical inventory purposes.

Group paths by hash:

```python
from collections import defaultdict


def find_duplicates(records: list[dict]) -> list[dict]:
    """Return groups of inventory records sharing the same SHA-256."""
    by_hash = defaultdict(list)

    for record in records:
        by_hash[record["sha256"]].append(record["path"])

    duplicates = []

    for sha256, paths in by_hash.items():
        if len(paths) > 1:
            duplicates.append({
                "sha256": sha256,
                "paths": sorted(paths),
            })

    return duplicates
```

## Why is this useful?

Duplicate identification can support:

- scoping repeated collected artifacts;
- finding identical binaries stored under different names;
- reducing redundant analyst review;
- understanding replicated configuration or tool files.

Again, identical content does not establish maliciousness.

# Lesson 16 — Build summary statistics

Create a report:

```python
def build_report(root: Path, records: list[dict], errors: list[dict]) -> dict:
    duplicates = find_duplicates(records)
    total_bytes = sum(record["size_bytes"] for record in records)

    return {
        "summary": {
            "root": str(root.resolve()),
            "files_hashed": len(records),
            "files_failed": len(errors),
            "total_bytes": total_bytes,
            "duplicate_groups": len(duplicates),
        },
        "files": records,
        "duplicates": duplicates,
        "errors": errors,
    }
```

This separates:

```text
summary → overall scan information
files → individual inventory records
duplicates → derived analysis
errors → incomplete processing information
```

That structure is easier for humans and programs to consume.

# Lesson 25 — Understand integrity baselines

A single inventory describes one point in time.

```text
Baseline A
file1 → hash X
file2 → hash Y
file3 → hash Z
```

A later inventory might show:

```text
Baseline B
file1 → hash X      unchanged
file2 → hash Q      changed
file3 → missing
file4 → new
```

This leads to a powerful defensive concept: **change detection**.

The next logical capability is comparing two inventories to classify:

- unchanged files;
- modified files;
- new files;
- removed files.

```bash
  --baseline previous_inventory.json
```

Desired analysis:

```text
UNCHANGED  config.txt
MODIFIED   notes.txt
NEW        nested/new-file.txt
REMOVED    old-file.txt
```

## Think before coding

You already have almost everything required.

A useful representation is:

```python
{
    "notes.txt": {
        "size_bytes": 25,
        "sha256": "..."
    }
}
```

Then ask:

```text
Is the path in both inventories?
    yes → are hashes equal?
              yes → unchanged
              no  → modified

Only in current? → new
Only in baseline? → removed
```

### Requirements

Your comparison should produce structured JSON containing:

```json
{
  "unchanged": [],
  "modified": [],
  "new": [],
  "removed": []
}
```

Do not treat a modification as malicious. Report the observed change and leave interpretation to the analyst.

# Completion criteria

Project 3 is complete when your tool can:

- accept a directory from the command line;
- validate that the target exists and is a directory;
- recursively discover files;
- produce deterministic file ordering;
- read files in binary mode;
- calculate SHA-256 using chunked reads;
- collect relative path and size metadata;
- continue when an individual file cannot be processed;
- preserve per-file errors for review;
- identify duplicate file content by hash;
- calculate overall scan statistics;
- export a CSV inventory;
- export a structured JSON report;
- print a concise terminal summary;
- avoid intentionally modifying source files;
- document analytical meaning and limitations.
